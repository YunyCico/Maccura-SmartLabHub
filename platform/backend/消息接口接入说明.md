# 首页消息接口接入说明

首页「Notifications Center」板块的数据源，后端统一走 `GET /api/messages`。

## 架构

```
home/src/views/HomeView.vue  ← 唯一消费方（已改造，原为写死的假数据）
  └─ home/src/api/messages.ts
       └─ GET /api/messages
            └─ app/services/message_service.py   并行拉三家 → 归一化 → 去重 → 排序
                 ├─ dingtalk_messages.py   钉钉：待办 / 工作通知 / DING / 日程
                 ├─ oa_messages.py         公司 OA：泛微 e-cology，路径全可配置
                 └─ salesforce_messages.py 暂缓接入，保留来源位
```

统一模型在 `app/services/message_models.py`：每家适配器把自己的原始结构
归一化成 `MessageItem`，首页只认这一个结构。

## 本地调试踩坑：端口与代理

**症状**：设置页所有按钮都没反应，接口报404 或 `{"detail":"Not Found"}`。

**根因**：本机同时存在两个后端实例，前端 Vite 代理默认写死 `http://localhost:8000`
（见 `home/vite.config.ts` 的 `SLH_API_TARGET`）。

排查顺序：

```bash
# 1. 看 8000 和 8010 各自是什么版本（旧实例缺新路由）
curl -s http://127.0.0.1:8000/api/integrations | head -c 60
curl -s http://127.0.0.1:8010/api/integrations | head -c 60

# 2. 看前端实际起在哪个端口（端口被占会自动 +1，容易被忽略）
grep -oE "http://127.0.0.1:[0-9]+" <前端日志>
```

**正确启动方式**（后端换端口时必须带环境变量）：

```bash
# 后端
cd platform/backend && python -m uvicorn app.main:app --host 127.0.0.1 --port 8010

# 前端：必须显式指定代理目标
cd home && SLH_API_TARGET=http://127.0.0.1:8010 ./node_modules/.bin/vite --host 127.0.0.1 --port 5173 --strictPort
```

`--strictPort` 很关键：没有它时 Vite 会自动跳到 5174，而你还在开5173 的旧页面。

## 健壮性约定

- **任一家失败不影响其他家**：每类消息单独 try/except，失败只记 error 字段。
- **未配置不报错**：凭据为空时该来源返回空列表，`/api/messages/sources` 显示未连接。
- **全部未配置时降级**：`using_placeholder=true`，返回 3 条示例数据，首页显示蓝色提示条。
- **字段映射缺失宁缺毋滥**：OA 没配 `title` 映射时直接返回空，不造无标题的假待办。

## 怎么填凭据

复制 `platform/backend/.env.example` 为 `platform/backend/.env`，然后：

### 钉钉

推荐走**设置页**（首页「Notifications Center」标题右侧的钉钉按钮 → 消息互通设置），保存后立即生效，无需重启后端。

手动配置等价于编辑 `platform/data/integrations.json` 的 `dingtalk` 段：

1. 钉钉开放平台 → 应用开发 → **企业内部应用 → 钉钉应用**（不要选「第三方企业应用」，
   那个需要先入驻成产品方案商，会被弹窗拦截）
2. 「凭证与基础信息」拿 `Client ID`（原 `AppKey`）/ `Client Secret`（原 `AppSecret`）
3. 权限管理开通：待办（Todo，读权限）、日历（日程读权限）
4. 填入设置页对应字段
5. `message_kinds` 控制拉哪几类（`todo,notify,ding,calendar`），默认四类全开

> 工作通知与 DING 无论开什么权限都拉不到数据，钉钉没开放收件箱查询接口（见下文）。

### 没有开发者权限怎么办（CorpId 拿不到）

钉钉开发者后台首页的 `CorpId` / `API Token` 需要开发者权限才可见，
没权限时会显示成 `************`。**这不影响接入**，代码里有三条降级路径：

| 凭据状态 | 走的通道 | 需要 CorpId |
| --- | --- | --- |
| 有 CorpId | `POST /v1.0/oauth2/{corpId}/token` | 是 |
| 无 CorpId | `GET /gettoken?appkey=&appsecret=` | 否 |
| 有 CorpId 但取 token 失败 | 自动回落到旧版 `gettoken` | 否 |

所以设置页里 **CorpId 是可选的**，只填 Client ID + Client Secret 就能跑。

同理，userid 也绕得过去：前端免登需要 CorpId，但没有 CorpId 时可以用
**手机号换 userid**——`POST /api/messages/dingtalk/userid`，body 传 `{"mobile":"138xxxxxxxx"}`，
底层走 `topapi/v2/user/getbymobile`，只依赖 access_token。设置页「手机号查 userid」按钮就是这个用。

> 注意别用 `topapi/v2/user/get` 查手机号——那是按 userid 反查用户详情，
> 传 mobile 过去会直接报 `Missing required arguments:userid`。

前端在钉钉容器内会自动免登换 userid；本地开发也可以在设置页直接填「默认 userid」，
或用上面的手机号按钮自动获取。

## 钉钉消息的真实接口（2026-10-20 实地探测确认）

共探测到 7 类，其中**只有 3 类在首页展示**（前 3 行）——
恒为空的（notify/ding）与无权限的（approval/attendance）已从 `_KIND_ORDER` 移除，
解析代码保留在 `dingtalk_messages.py` 里，可用时加回一行即可恢复。

> 早期版本里的路径（`topapi/v2/todo/list`、`topapi/message/corpconversation/list`、
> `oapi/calendar/users/{userid}/calendars`）**全部是错的**，实测均返回
> `Invalid method[不合法ApiName]`。下面这批是拿真实 token 逐个试出来的。

| 类型 | kind | 接口 | 实测结果 | 首页展示 |
| --- | --- | --- | --- | --- |
| 待办任务 | `todo` | `POST /v1.0/todo/users/{unionId}/org/tasks/query` | ✅ 通，权限「待办应用中待办读权限」已开 | ✅ |
| 个人日程 | `calendar` | `GET /v1.0/calendar/users/{unionId}/calendars/primary/events` | ✅ 通，实测取到 11 条日程 | ✅ |
| **部门行程** | `trip` | `GET /v1.0/calendar/users/{unionId}/calendars` → 逐个 `.../calendars/{calendarId}/events` | ✅ 通，取到「实验室运营管理部-行程日历」24 条医院回访行程 | ✅ |
| 工作通知 | `notify` | — | ❌ **钉钉未开放收件箱查询接口** | ❌ 已下线 |
| DING 消息 | `ding` | — | ❌ **钉钉未开放收件箱查询接口** | ❌ 已下线 |
| 审批 | `approval` | `POST topapi/processinstance/list` | ⚠️ 路径对，缺权限 `qyapi_aflow` | ❌ 无权限 |
| 考勤 | `attendance` | `POST attendance/list`（**无 topapi 前缀**） | ⚠️ 路径对，缺权限 `qyapi_get_attendance_data` | ❌ 无权限 |

### 部门行程是本轮最有价值的发现

之前只查了 `calendars/primary`，漏掉了**已订阅的部门日历**。
正确姿势是先列日历、筛出 `type == "subscribed"` 的，再按 `calendarId` 逐个取事件：

```python
cals = (resp.get("response") or {}).get("calendars") or []
subscribed = [c for c in cals if c.get("type") == "subscribed" and c.get("id")]
```

实测返回 24 条「XX医院-6s实施、运营回访」行程，正是实验室运营管理部的实际工作安排。

**全天日程用 `start.date`（`"2026-09-07"`），定时日程用 `start.dateTime`
（`"2026-10-21T15:00:00+08:00"`），两种都要认**，见 `_calendar_item()`。
全天日程的时间文案显示「今天 全天」，不显示假钟点。

### 审批与考勤只差权限

钉钉遇到未开通的权限会返回带申请链接的错误，原样透出到首页说明条，直接点链接申请：

- 审批 `qyapi_aflow`：`https://open-dev.dingtalk.com/appscope/apply?content=dingaadldrx3nvfxjceo%23qyapi_aflow`
- 考勤 `qyapi_get_attendance_data`：`https://open-dev.dingtalk.com/appscope/apply?content=dingaadldrx3nvfxjceo%23qyapi_get_attendance_data`

注意考勤路径**没有 `topapi` 前缀**，是旧版网关的历史遗留，别顺手加上去。

### 已确认无效的路径（别再试）

| 路径 | 错误 |
| --- | --- |
| `topapi/v2/department/listsub`、`topapi/v2/user/list` | `ERR(50004)` 部门id不在授权范围内（通讯录全量读取需单独申请） |
| `v1.0/workflow/processes/instanceIds/query` | 缺权限 `Workflow.Instance.Read` |
| `v1.0/workflow/premium/processCentres/noticedInstances` | 缺权限 `Premium.Workflow.ReadWrite.All` |
| `v1.0/attendance/checkin/records/query` | 缺权限 `qyapi_checkin_read` |
| 待阅 / 公告 / 任务 / 工作日志 / 群列表 / 机器人发送 | `Invalid method` |

判读方法论：`Invalid method` / `InvalidAction.NotFound` = 路径不存在；
`InvalidVersion` = 路径命中但版本参数不对；
`Forbidden.AccessDenied.AccessTokenPermissionDenied` = **路径对，只差权限**。

### v1.0 网关与旧版网关的三处差异（踩坑重灾区）

1. **鉴权位置**：v1.0 用请求头 `x-acs-dingtalk-access-token`，
   不是旧版的 query 参数 `access_token`
2. **响应结构**：v1.0 成功响应是**顶层平铺**的 —— `todoCards` / `events` / `calendars` 直接挂在根上，
   **没有 `result` 包裹**。按旧版的 `resp["result"]["list"]` 取值会永远取到空
   （例外：`calendar/.../calendars` 列表接口有一层 `response.calendars`）
3. **错误格式**：v1.0 用 `code` + `message`（如 `code: "InvalidParameter.xxx"`），
   旧版用 `errcode` + `errmsg`

### 为什么需要 unionId

v1.0 的待办与日程都以 **unionId** 做路径参数，userid 换不来。
转换链：`userid` → `topapi/v2/user/get`（传 userid）→ `unionid`。
一次首页刷新里换算一次并缓存，不重复打接口。

### 时间参数格式

钉钉的 v1.0 网关要求 **ISO8601 带冒号的时区**（`+08:00` 或 `Z`）。
Python 的 `strftime("%z")` 出来是 `+0800`，会被拒
（`InvalidParameter.ParsedISO8601TimestampError`）。用 `datetime.isoformat()`。

### 工作通知 / DING 为什么拉不到

不是配置问题，是**钉钉开放平台确实没有提供收件箱查询接口**：

- 工作通知只有发送侧：`topapi/message/corpconversation/asyncsend_v2`（发）、
  `getsendprogress`（查发送进度）、`getsendresult`（查发送结果）、`recall`（撤回）
- DING 只有「发送DING消息」和「撤回已经发送的DING消息」

已经实地探测过 20+ 个候选路径（`topapi/message/*`、`topapi/ding/*`、
`v1.0/ding/*`、`v1.0/robot/ding/*`、`v1.0/im/dings/*` 等），全部返回
`Invalid method` 或 `InvalidAction.NotFound`。

因此这两类**不在首页占板块**（2026-10-20 起下线）——
它们恒为空，留着只会让通知中心看起来像坏了。
实现方式是把这两种 kind 从 `_KIND_ORDER` 里移除：
`enabled_kinds()` 会按 `_KIND_ORDER` 过滤，
所以即使老的 `integrations.json` 里还残留着 `notify,ding`，也不会冒出空板块。
`_fetch_notify` / `_fetch_ding` 的代码与「未开放」说明文案都保留在文件里，
钉钉开放后加回 `_KIND_ORDER` 一行即可恢复。

同理，**设置页关掉的类型在首页直接不渲染**（前端 `dingtalkKinds` 先 filter 再 map），
而不是显示成一个灰色空板块。

如果后续要接通知与 DING，得走**事件订阅**（钉钉推给应用）而不是轮询。

### 公司 OA（oa.maccura.com，泛微 e-cology）

**实测结论（2026-10-20）**：

- 系统确认为泛微 e-cology：Cookie 名 `ecology_JSessionId`，登录页 `/login/Login.jsp`
- 所有 `/api/*` 未登录时统一返回 `{"msg":"用户信息为空","errorCode":"001","status":false}`
  —— 状态码恒为 200，**无法通过探测区分真实端点和虚构端点**
- `/services/` 下暴露 XFire SOAP 服务（WorkflowService、HrmService 等），可作备选

所以路径**没有写死默认值**，必须先确认再填：

1. 浏览器登录 OA，按 F12 打开 Network，找「我的待办 / 已办」那条请求
2. 把它的路径、查询参数、响应结构填进去：
   - `OA_TODO_PATH` = 请求路径，如 `api/workflow/paService.do`
   - `OA_TODO_QUERY_PARAMS` = 查询串，如 `userId=xxx&pageSize=20`
   - `OA_ROWS_PATH` = 列表在响应里的位置，如 `result.todos`
   - `OA_FIELD_MAP` = 字段映射，**至少要有 title**

`OA_FIELD_MAP` 示例：

```json
{"title":"subject","due":"finishTime","creator":"creator","id":"workflowid","url":"link","priority":"urgency"}
```

鉴权两种模式：

- `OA_AUTH_MODE=password`：需同时填 `OA_LOGIN_PATH`、用户名、密码
- `OA_AUTH_MODE=token`：填 `OA_TOKEN`；`OA_AUTH_HEADER` 填自定义头名（如 `X-Token`），留空则当 Cookie 发

## 配置接口（设置页用）

配置存在 `platform/data/integrations.json`，与 `.env` 分离：`.env` 放数据库等基础设施配置，
三家消息接口的凭据放 JSON 文件，可通过界面修改，**保存后立即生效，无需重启后端**。

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/integrations` | 读配置（密码脱敏）+ 各来源缺失项 |
| PUT | `/api/integrations` | 保存配置（白名单校验） |
| POST | `/api/integrations/test` | 连通性自检，不落盘 |

安全约定：

- 密码类字段（AppSecret / password / token / secret）**读取时一律返回空串**，
  只额外给一个 `*_configured` 布尔值
- 前端回传空密码视为「不修改」，不会把已保存的密码擦掉
- 只接受白名单内的键，`__class__` 之类无法写入
- 写入用临时文件 + `os.replace` 原子替换，不会写出半截配置

## 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/messages?user_id=&limit=50` | 三家聚合后的待办列表 |
| GET | `/api/messages/sources` | 各来源配置状态，不拉数据 |
| POST | `/api/messages/dingtalk/userid` | 手机号换钉钉 userid（body 传 mobile + 可选凭据） |

响应结构：

```json
{
  "items": [{
    "source": "dingtalk",
    "source_label": "钉钉",
    "tone": "blue",
    "title": "确认本周实验室服务问题汇总",
    "detail": "钉钉待办 · 创建人 张三",
    "due": "今天 15:00",
    "priority": "高",
    "url": "...",
    "category": "待办",
    "kind": "todo",
    "live": true
  }],
  "sources": [
    {
      "source": "dingtalk",
      "enabled": true,
      "count": 12,
      "error": "",
      "kinds": ["todo", "notify", "ding", "calendar"],
      "kind_notes": {
        "notify": "钉钉未开放工作通知的收件箱查询接口（官方只有发送接口），该板块暂无数据。",
```

`kind_notes` 是**逐类型**的说明，首页每个子板块各自展示：
钉钉哪一类没数据、为什么（未开放接口 / 缺权限 / 调用失败）。
比笼统的 `reason` 更能定位问题。
